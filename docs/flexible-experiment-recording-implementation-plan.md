# 灵活实验记录第一阶段实施计划

日期：2026-10-17  
状态：源码探查后的实施方案；代码已实施，实际选型、测试和待验收项见[实施记录](flexible-experiment-recording-delivery.md)。以下保留原计划，不能将阶段退出条件直接视为全部已验收。

需求依据：[第一阶段需求基线](flexible-experiment-recording-requirements.md)。本计划不增加模板、合成/测试强制分类、独立 OCR、实时仪器操作或文献管理功能。

## 1. 结论与实施原则

本次变更是实验内容模型升级，不只是详情页增加动态字段。现有固定 Schema 贯穿 Agent 状态、再次提取、仓储、日志、检索、分析、打印和导入入口。

推荐保留 React、Flask、SQLite、账号作用域、编号、附件仓储及主/子会话机制，在这些基础上增加版本化实验文档和统一写入服务。先建可信的数据与审批通路，再接入编辑器和 Agent，最后统一所有读取方。

核心决策：

1. 基本信息与正文分离；正文只有“实验条件、实验过程、结果与分析”三个板块和一层子字段。
2. V2 正文是唯一可编辑事实来源；旧固定字段不能与 V2 双向维护。
3. 普通内容更新直接保存；结构修改通过持久化方案及用户手动确认实施，权限由服务端校验。
4. 模型负责组织内容，不在最终保存时用固定 Schema 重新提取一次；保存应是确定性校验与持久化。
5. 兼容旧记录与旧会话，但禁止旧写接口绕过新格式约束。
6. 保留现有外壳、配色、字体、分栏和手机布局；正文按新需求组织，流程图等新控件沿用既有视觉语言。

## 2. 源码探查：模块与真实调用链

### 2.1 当前记录生成链

```text
聊天组件 / agent-client.js
  → POST /api/agent/message 或 /message/stream
  → AgentLoop.run / run_stream
  → start_record_thread、update_schema
  → _schema_context（固定字段）
  → generate_record / ToolExecutor._generate_record
  → lib.parser.parse_notes（再次调用 structured_extract）
  → EXPERIMENT_SCHEMA
  → _generated_preview
  → routes/api_agent.py 自动保存
  → SqliteExperimentRepository.save
```

重要事实：`generate_record` 工具说明称不会二次提取，但当前 `_generate_record` 的实现实际会调用 `parse_notes(enhanced_notes, loop.llm)`；失败再走 `_build_preview`。不能只依据工具描述制定方案。

`POST /api/agent/confirm` 目前转调 `/api/parse/confirm` 的保存逻辑，不是结构审批。新审批不能复用这个名称就视为已经有权限保障。

## 3. 推荐数据模型

### 3.1 记录格式与数据库版本分开

新增实验正文格式 `format_version=2`。数据库当前实验仓储标记为 `_SCHEMA_VERSION=6`；数据库迁移号单独递增，不能和文档格式号混用。旧记录没有 V2 正文时按旧格式读取。

保留基本信息、账号、附件链接和归档等现有外层字段；正文结构示意：

```json
{
  "format_version": 2,
  "sections": [
    {"id": "conditions", "fields": []},
    {"id": "process", "fields": []},
    {"id": "results", "fields": []}
  ],
  "sources": []
}
```

`sections` 必须恰好是上述三个固定身份及顺序，中文标题由产品定义；不让模型自建第四板块。子字段使用稳定 ID，与显示名称分离；字段数组决定顺序。

字段最小结构：`id、label、kind、presentation、content、note、source_refs`。`kind` 是内容类型，不是实验类型；不允许 children 或递归字段。元数据、内容和布局有分别的更新规则。

### 3.2 五类内容结构

| kind | 内容结构建议 | 验证重点 |
| --- | --- | --- |
| text | 原始 Markdown/文本，格式显式标记 | 新内容不接受任意 HTML；旧 HTML 经兼容清洗后显示 |
| table | 稳定 column ID、row ID、cells，备注可选 | 列名/列类型属于结构；行与单元格是内容；禁止嵌套子表单 |
| process | 物质节点、动作及连接关系、独立布局 | 参数不嵌入绘图字符串；端点引用存在；删除节点不得留下悬空动作 |
| formula | LaTeX 源文、变量/单位说明、代入过程及结果文本 | 渲染与求值分开；无任意代码执行；不将计算值标为实测值 |
| assets | 指向账号附件的引用及说明 | 存 SHA-256 等身份，不存本机路径；服务端校验访问和关联权限 |

第一阶段公式必做可编辑 LaTeX 和计算过程展示；通用数值求值器不是首期放行前提。若实现有限求值，必须限定表达式和单位规则、使用确定性计算，并单独测试，不调用 eval 或信任 LLM 数字。

只在内容确实涉及共享物质时引入轻量对象 ID，用于表格条目与流程节点引用同一对象。对象数据有唯一归属，视图显示通过引用获得，避免两处改名互相覆盖；不建设独立样品管理产品或强制关系录入表单。

### 3.3 流程图不直接以绘图库格式作为领域格式

推荐领域模型为物质节点 `nodes` 和动作 `actions`：动作有稳定 ID、`source_ids、target_ids、label、parameters、repeat_note、note`。参数保存 ID、名称、原值、单位及来源，允许未注明单位。

一个混合动作可以有多个输入和输出；同一动作可渲染成多条连线，但共享一个动作 ID 和参数集合，编辑一次即可同步。视觉上仍是物质矩形与动作连线；可使用连接汇合点，不新增“操作矩形”冒充物质。

节点位置、缩放等保存在独立布局部分，不参与化学事实解释。切换步骤视图时，存在并行或分支就显示明确关系，不把它伪装成唯一线性顺序。

### 3.4 持久化建议

在现有 `experiments` 表增量增加 `format_version、document_json、summary_text、search_text`，不为每个自定义字段建 SQL 列，不引入 EAV 或新数据库。V2 读取时解析 document；旧列保留作历史兼容，不再作为 V2 的可编辑副本。

增加三个小型持久化表：

- `record_drafts`：账号、draft_id、关联会话、正文、基本信息、revision、来源及待整理输入引用；允许没有正式实验编号的记录持续整理。
- `record_structure_proposals`：账号、proposal_id、目标类型/ID、base_revision、规范化方案、摘要哈希、状态、应用结果及时间；支持刷新和重启恢复。
- `experiment_revisions`：账号、实验 ID、revision、完整可恢复快照、来源、关联 proposal/请求 ID；更新摘要不能替代此表。

草稿沿用相同正文校验器、操作模型及版本机制，不再维护第二套可编辑 `_schema_context`。会话状态保存草稿引用和运行上下文；上下文压缩不能删除尚未确认的真实输入或结构方案。

派生 `summary_text/search_text` 用确定性遍历生成，排除无意义布局数据；不让 LLM 自行撰写摘要后当作唯一检索内容。摘要长度受限，完整搜索文本只在后端索引，列表保留轻量投影。

## 4. 统一写入、版本与结构审批

### 4.1 新增模块边界

- `lib/core/record_document.py`：Pydantic 正文类型、结构签名、兼容呈现规则与内容验证。
- `lib/services/record_document.py`：内容操作、结构方案、应用、发布、恢复及引用继承；现有入口统一调用这里。
- `lib/services/record_projection.py`：全文、摘要、模型语义投影、旧字段到三板块的确定性读取适配。
- 新草稿/结构方案/完整版本仓储：只做数据库访问，不读取 Flask 请求或调用模型。
- `lib/services/attachment_reader.py`：从 Agent 巨型文件中迁出本阶段需要改的页面准备、视觉读取与来源处理。

模块名称为计划建议，不在本轮创建空实现或通用框架。旧实验服务继续管理既有引用、归档等，减少无关重构。

### 4.2 不相信调用方对权限的自我描述

内容接口只接受限定的元信息、既有字段内容、合法呈现和布局更新。后端将操作前后结构签名比较：板块归属、字段 ID/名称/类型、表格列定义等不得通过内容更新改变。

结构方案可增删字段、改名、移动、转换类型、合并拆分；方案必须同时包含转换后的内容，供用户审阅。动作内部节点、参数与表格数据行属于内容，不误归类成子字段新增。

确认不能由模型提交 `confirmed=true`。专用 HTTP 接口从已认证浏览器接收手动决定，Agent 工具没有这个接口或批准 token。前端展示服务端规范化方案，不展示一份与实际执行不同的模型描述。

批准时重新检查账号、目标、角色范围、base_revision、方案身份与状态；原子地应用正文、生成版本和日志、置方案为 applied。重复请求返回同一次应用结果，不能再次执行。过期、拒绝、取消、目标版本冲突和目标不可访问必须清楚区分。

初次建字段批量审批一次。等审批时保留原始输入及候选内容，可继续记原始信息，不因用户离开页面或断线丢失。新增内容改变了待批方案时产生新版本/新方案，不能让旧批准覆盖新方案。

### 4.3 事务是前置工作

`ThreadSafeConnection` 当前设置 `isolation_level=None`，每条 DML 自动提交；仅在服务中顺序调用 save、append、update proposal 不会自动组成事务。

新增有限的事务上下文，保持已有全局写锁与连接锁的取得顺序，在同一连接内 BEGIN/COMMIT/ROLLBACK；审查仓储内 commit，不允许中途提前结束外层事务。网络/模型调用必须在数据库事务外完成。

正式内容修改、完整版本、日志、派生搜索文本及审批状态一起提交。资源变更通知在成功提交后发送。事务失败测试必须验证没有半份记录、伪日志或被错误消费的批准。

### 4.4 撤销与恢复

先做完整版本恢复：以当前 expected_revision 为条件，将选定旧快照生成一个新版本，不删除后续历史。附件二进制不复制，引用保持权限与可用性校验。

LLM 请求恢复导致字段结构变化时仍须经过结构审批；用户本人在版本界面直接操作属于手动修改。不能用恢复接口绕过结构权限。上线前无法完整恢复的旧日志不伪装成可撤销版本。

## 5. HTTP 接口实施方案

以下新增路径为建议契约，实施 P0 阶段固定。保持现有认证、同源写保护、no-store、账号隔离和 409 语义。

### 5.1 现有接口处理

| 现有接口 | 实施方式 |
| --- | --- |
| `GET /api/v1/experiments/<id>` | 增加 format_version/document；旧记录提供确定性兼容视图，不因 GET 落库升级 |
| `GET /api/v1/experiments`、`/experiment-list` | 增加通用摘要/匹配结果，保持分页和轻量列表，移除固定字段依赖 |
| `POST /experiments/<id>/save-json` | 旧记录暂兼容；V2 不接受旧全量字典直写，引导新操作接口，不能忽略 document 后返回成功 |
| `POST /experiments/<id>/regenerate` | V2 改为重新组织建议，不能走固定提取直接覆盖 |
| `POST /api/parse`、`/parse/confirm`、`/api/agent/confirm` | 新格式走同一草稿/审批/发布服务；不允许前端提交自造 ID 或任意已批准正文绕过流程 |
| `POST /api/agent/message`、`/message/stream` | 两条路径使用同一应用服务；不再对新生成结果直接调用 repo.save |
| `POST /api/exp/<id>/chat`、`/confirm` | 沿用当前实验作用域，应用相同内容/结构规则 |
| `/api/agent/selection` | 保留分析实验选择语义，不赋予结构批准权限 |
| 附件上传、下载、预览接口 | 继续复用；新增来源页码定位，不重建附件存储 |
| `GET /experiments/<id>/yaml`、`/<id>/print` | 输出当前格式，正文不遗漏；旧数据仍按兼容路径输出 |

### 5.2 建议新增接口

| 接口 | 用途与约束 |
| --- | --- |
| `POST /api/v1/record-drafts` | 创建空草稿及三个空板块，无模板、无必填类型 |
| `GET /api/v1/record-drafts/<id>` | 恢复当前草稿、revision 和待批方案摘要 |
| `POST /api/v1/record-drafts/<id>/operations` | 用 expected_revision + request_id 更新内容，禁止偷改结构 |
| `POST /api/v1/record-drafts/<id>/publish` | 把当前已确认正文发布为正式记录；幂等返回同一实验 ID，不要求填满固定字段 |
| `POST /api/v1/experiments/<id>/operations` | 正式记录内容操作，CAS 保存，返回新 revision 和变更摘要 |
| `GET /api/v1/structure-proposals/<id>` | 读取完整待批方案、差异和状态 |
| `POST /api/v1/structure-proposals/<id>/resolve` | 手动批准/拒绝/取消；请求只引用方案身份/版本，不传入替换正文 |
| `POST /api/v1/record-drafts/<id>/structure-proposals`、`/experiments/<id>/structure-proposals` | 用户/Agent 提交结构建议，不能提交即批准 |
| `GET /api/v1/experiments/<id>/revisions`、`/revisions/<revision>` | 查看完整可恢复版本，区分摘要与快照 |
| `POST /api/v1/experiments/<id>/restore` | 手动恢复到新版本，校验当前 revision 与附件引用 |

共用错误码：`revision_conflict`、`structure_change_requires_confirmation`、`invalid_document`、`proposal_not_pending`、`vision_unavailable`；不存在或无权访问沿用 404，未登录 401，正文验证失败 422，版本冲突 409。错误包含可读说明和必要的当前版本，不回传其它账号资料。

同 request_id、同目标、同请求内容重复提交应返回原结果；同 request_id 携带不同内容应拒绝。草稿发布、结构批准、普通更新都要处理网络重试，不能靠客户端防双击保证。

## 6. Agent 工具与对话适配

### 6.1 工具契约

- 保留搜索、读取、历史、附件、归档等既有名称与作用域；`read_experiment` 返回完整 V2 正文及稳定字段 ID。
- 建议新增 `propose_record_structure`，只创建并返回结构方案卡片，不执行批准。
- `update_schema` 的新格式参数改为有限内容操作，或由新 `update_record_content` 替代；上线时只暴露一种当前写工具，避免模型在两套协议间选择。
- `modify_experiment` 的 V2 分支使用相同内容操作与服务端签名检查，不接受任意顶层字段字典；结构变更返回需提案，不静默忽略。
- `generate_record` 发布已持久化且已批准的草稿，不调用旧 parse_notes，不二次改写事实。保留工具名称和生成卡片有利于减少前端协议变化。
- `load_reference` 仅处理历史旧调用，新模型继续使用 `read_experiment(as_reference=true)`。

工具 executor 除参数校验还应核对当前模式/角色允许清单。仅从模型看到的工具列表移除某工具不足以作为新审批的执行保障；本次按新读写服务边界补上必要校验。

### 6.2 消除固定字段思维

替换 `_schema_context`、`merge_context`、`_build_schema_status`、`_build_notes_from_context`、`_build_preview` 及新路径上的 `_core_fields_filled` 假设。新状态摘要是已确认结构、实际内容、待批方案与真实疑问，不是“已填 12/16”。

移除新路径对 `EXPERIMENT_TYPES` 优先级与标签推断类型的依赖，不新增 synthesis/test 枚举。不按固定栏目催问，不用默认 no_anomalies=true 把未记录变成无异常。

新增结构提案/内容写入应被算作对话进展，检查现有无进展计数与线程自动结束逻辑，避免等用户确认时误取消。同步修改 run 与 run_stream，或只抽取它们共同的本次新增业务操作，避免顺带重写整个循环。

### 6.3 历史条件继承

父 Agent 仍可按现有权限搜索历史资料，实验编辑子 Agent 仍限当前实验，不借新需求放开历史检索范围。需要历史继承的任务由当前具备该能力的主 Agent 处理。

用户明确要求沿用、目标可确定且读取成功后，可直接写既有字段内容并告知引用与版本；遇到本记录需要新增字段时，仅字段结构部分走人工审批，不额外要求用户再次确认已明确授权的历史条件。

继承不复制旧结果与结论。因用户明确指定差异产生的新值不视为必须求证的冲突；无明确修改语义的真实矛盾才提问。

### 6.4 会话恢复

旧 state 中的 context 按旧版本恢复，转为兼容草稿并保留输入，不自动生成新的嵌套字段。运行状态增加版本标记，正式正文只从文档仓储读取。

待批卡片从 proposal 仓储恢复，不靠历史消息里的 status；过期卡片只读，不因恢复会话触发应用。方案批准与继续对话分开：应用成功即是真实保存，LLM 后续解释失败也不能回滚已批准事实或再次执行修改。

## 7. React 编辑与渲染实施

建议新增 `frontend/src/features/record-document/`，集中放正文 types、三板块组件、字段 renderer/editor、结构差异与来源组件。实验详情继续负责加载、元信息、归档、附件、子对话和保存反馈。

组件建议：`RecordDocument、RecordSection、RecordField、TextField、TableField、ProcessField、FormulaField、AssetsField、StructureProposal、SourceLink`。不为单一组件引入通用插件框架，类型分派使用有限显式映射。

初期先让手动编辑跑通文本/表格及结构确认。再增加流程图、公式、原生视觉自动整理。用户可直接手动调整结构；模型建议通过结构卡片批准。草稿与已保存值分离，409 时保留未保存改动，不自动重试覆盖。

表格用稳定行列 ID 保存数据，不用数组下标作为长期身份。支持可变列、行、单元格、备注；列结构变动与数据内容变动分别识别。

流程图编辑候选为 React Flow：其自定义边和标签能力可承载动作及参数编辑。接入前做小范围验证：多输入/输出动作共享、移动端编辑、保存恢复、打印。不要把绘图库 Node/Edge 类型泄漏为后端唯一数据协议。

公式渲染候选为 KaTeX，本地打包字体与样式，错误时保留源文可编辑；禁用信任任意 HTML/外部命令的配置，限定资源规模。新字段局部清洗富文本和链接，保持旧 Markdown 输入的兼容，不能只在客户端过滤。

打印布局使用新正文视图模型，文本/表格/公式正常排版，流程图输出静态 SVG 并处理分页；不能截图一个可能未加载完的交互画布作为唯一正文。现有 Jinja 打印入口可保留数据壳，新增 V2 打印入口脚本使用只读组件，避免在 Jinja 再手写五套渲染规则。

只有图形坐标变化不应令历史分析被判为事实过期；事实投影与展示布局分离后，相关检查以事实投影为准。

## 8. 原生多模态与来源

现有 `describe_image` 已把像素交给当前模型，但返回的是脱离任务上下文的概括文本；现有 PDF 路径只提取前 30 页文本。这两条都不能直接视为完整的手写实验整理能力。

实施内容：

1. 保留附件原件；上传后复用现有账号附件身份，不再创建第二套文件库。
2. 用 Pillow 处理方向、大小与裁切，PDF 使用页面渲染库转为图像，默认不做独立 OCR。
3. 在 `LLMClient` 增加有任务上下文的多图读取/结构化提议能力，传入文件身份、页码与本次整理目标；使用原图语义组织正文，禁止只传旧概括文本丢掉依据。
4. 按页面分组读取，返回内容及 source_refs；不跨页截断后声称读完；超限时明确说明未读取范围并支持继续。
5. 最少来源结构：附件 SHA-256、页码、原文摘录/用户消息身份、来源类型。历史继承附实验 ID、revision 与字段身份；区域坐标可选且标注是否已验证。
6. 处理失败保留已完成结果和输入，重试不重复创建实验；无视觉能力明确返回，不降级为编造文字。
7. 来源页面定位沿用附件预览扩展，先完成 PDF 页码跳转和图片原件查看，再考虑精确区域高亮。

PDF 渲染候选为 pypdfium2；当前 requirements 只有 pypdf 和 Pillow 等，尚没有页面渲染依赖。依赖版本、Windows/Linux wheel、许可证和部署包体需验证后锁定，不在本计划中假设已经安装。

首期为少量页面设置明确的页面数、像素总量、单页尺寸、超时与模型上下文限制；P0 用真实样本确定数值。不借此阶段建设批量任务调度平台；保留页面处理进度和候选结果已足够，模型调用继续采用现有服务端运行方式。

## 9. 搜索、引用、分析与旧功能兼容

- 搜索：FTS 当前只索引 title/purpose/conclusion/original_notes，需要迁移触发器与索引，加入确定性正文搜索文本；列表、模糊引用解析和 Agent 搜索摘要一起适配。
- 列表：原 `matches` 在客户端查 sop/materials 等，不能简单删除而使正文关键词搜索失效。把正文匹配交给服务端，保留轻量摘要、标签与时间筛选；新旧格式用同一确定性投影，不把全文装入所有卡片。
- 对比：先实现按主板块展示每份记录的字段，不因同名合并不等价字段；高级自动对齐不属首期要求。
- 分析：证据包保存完整 V2 正文、来源及所用版本；模型输入用语义投影去掉坐标。旧报告快照保持原样，过期判断识别旧/新版本及确定性兼容投影，避免仅迁移格式即宣称实验事实已变。
- 引用：不能只从 original_notes 的实验编号正则重建引用，否则新 source_refs 的引用会丢失。显式来源与既有引用合并、去重，继承仍受工具权限控制。
- 附件：正文引用只能指向已有合法附件，不能通过修改正文给自己关联别人的文件；移除附件与正文引用一致性要提示或在同一事务中处理，不留下无说明的断链。
- YAML/打印：导出含格式号、板块、类型与来源，公式和流程图不被压成空字符串。
- 现有模板页：本阶段停止作为新记录入口或依赖，从导航中移除模板引导；不自动删除用户已有模板文件。历史 API 的保留/退役需要调用方审计，但不能继续驱动新记录流程。

## 10. 旧记录、旧会话与发布

### 10.1 确定性兼容读取

旧记录 GET 不修改数据库、不调用模型，适配到三板块：

| 旧内容 | 兼容呈现 |
| --- | --- |
| purpose/materials/equipment | 实验条件中的文本或表格 |
| sop/process_parameters/observations | 实验过程；旧 SOP 先保持步骤文本，不推测中间物质画图 |
| results/conclusion/next_steps | 结果与分析；下一步保留未来语义 |
| characterization/experimental_plan | 按旧字段原意保留为表格与标记说明，不能把表征计划或预期结果变成已执行事实 |
| original_notes/附件/引用 | 原文及来源保留，未知旧扩展内容保持可查看，不为统一展示丢弃 |

旧默认 observations.no_anomalies=true 不能证明用户说过无异常，转换不得新增事实断言；原有值作为旧数据保留并说明来源。计划行、未来想法不得被新主板块名称误导为实际完成。

### 10.2 写入升级和回退

新建记录写 V2。旧记录首次编辑升级时展示确定性映射方案，经用户手动确认后保存 V2 和完整旧快照；之后只编辑 V2。旧字段列保留但不双写，过时客户端的旧字段修改应明确拒绝，不返回假成功。

不在开发阶段扫描、转换或导入真实旧库。发布前对授权备份做迁移演练与数量/内容校验，数据库先做增量迁移，所有读取方适配完成后才开放 V2 新建。

回退必须区分代码和数据：产生 V2 后不能直接部署只懂旧字段的版本。应回到已具备 V2 只读兼容的发布版本，或停写后恢复一致的数据库/附件备份；不能承诺旧代码无损编辑新内容。

## 13. 主要风险及控制

1. 动态字段被旧仓储白名单丢弃：先增加明确 V2 方法及旧写入口限制，不能先上线前端。
2. 工具描述与执行不一致：以实际调用链为准，特别移除再次固定提取和路由直写。
3. 所谓批准只是模型口头确认：方案内容、版本和应用结果在服务端持久化，批准入口不属于 Agent 工具。
4. 原有摘要日志无法撤销：新增完整版本；历史摘要不宣称可恢复。
5. 图形漂亮但不能改、不能打印：领域数据与绘图库分开，P0 验证多输入动作、手机编辑及静态输出。
6. 视觉识别概括丢细节：任务上下文、页码来源、原件对照及未知标记；以真实样本测试，不要求模型输出虚假确定性。
7. 兼容期间双重事实：V2 只存一份可编辑正文，列表/分析/打印由同一投影产生，旧列不反向覆盖。
8. 计划功能借迁移混入：保留旧计划文字的未来语义，但不在首期新增计划产品或模板工作流。

## 14. 技术候选的官方依据

以下仅用于本计划的候选能力核实，不表示已安装、已锁版本或已通过项目样本验收：
